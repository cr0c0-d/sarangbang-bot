## 1. ★ 왜 진단부터인가

이 저장소에서 **같은 사고가 두 번** 났습니다.

- **고정 주소 `@handle/live`** — 공개 채널로만 확인하고 일부공개까지 된다고 단정했다가,
  소유자가 실제로 막혔습니다.
- **ffmpeg 종료코드 183** — 두 사실을 확인하고 원인을 쿠키라고 단정했는데, 실제 원인은
  **화면 없는 방송**이었습니다.

둘 다 **실측한 조건 밖으로 결론을 늘린** 것입니다. 음성 수신에는 그 위험이 셋 있고,
셋 다 **토큰 없이는 알 수 없습니다.**

1. **봇의 귀를 열 수 있는가.** 지금 `guild-audio.js` 는 `selfDeaf: true` 로 들어갑니다.
   **귀를 막은 봇은 아무것도 받지 못합니다.** `connection.rejoin({ selfDeaf: false })` 로
   커넥션을 끊지 않고 열 수 있을 것 같지만 **확인 못 했습니다.**
2. **패킷이 도착하는가.**
3. **도착한 패킷을 복호화할 수 있는가.** 디스코드가 음성에 **DAVE(종단간 암호화)** 를
   깔고 있습니다. `@discordjs/voice` 가 `@snazzah/davey` 를 의존성으로 갖고 있어
   처리되는 것처럼 보이지만, 실제로 되는지는 **확인 못 했습니다.**

→ 그래서 **세는 것만 하는 진단**을 먼저 넣었습니다. 소리는 저장하지 않습니다.

### 진단이 어떻게 세 갈래를 구분하는가

`@discordjs/voice` 0.19.2 의 수신 경로(`VoiceReceiver.onUdpMessage`)를 읽어 확인한 사실입니다.

```js
this.speaking.onPacket(userData.userId);   // ← 복호화 **전**
const stream = this.subscriptions.get(userData.userId);
if (!stream) return;
...
const packet = this.parsePacket(...);      // ← 복호화
if (packet) stream.push(packet);           // ← 복호화 **후**
```

**`말하기` 신호는 복호화 전에, `opus 패킷` 은 복호화 후에 올라옵니다.** 그래서 두 숫자를
따로 세면 무엇이 막고 있는지가 갈립니다.

| 말하기 | 패킷 | 진단 |
|---|---|---|
| — | — | 봇이 아직 귀를 막고 있음 → `rejoin` 으로는 안 열린다 |
| 0 | 0 | 아무 신호 없음 (**아무도 말하지 않았을 수도 있음**) |
| 있음 | **0** | ★ **도착은 하는데 복호화가 안 된다** — DAVE 를 의심할 근거 |
| 있음 | 있음 | ✅ 수신됨 |

봇이 귀를 막았는지는 우리가 보낸 요청이 아니라 **디스코드가 알려주는 실제 상태**
(`guild.members.me.voice.selfDeaf`)를 읽습니다. 요청이 먹혔는지를 요청으로 확인하면 안 됩니다.

### 읽어주기·음악과 부딪히지 않는가

**부딪히지 않습니다.** `self_deaf` 와 `self_mute` 는 다른 것이기 때문입니다.

| | 뜻 | 진단이 바꾸는 것 |
|---|---|---|
| `self_deaf` | 내가 **안 듣는다** | ✅ 이것만 잠깐 끕니다 |
| `self_mute` | 내가 **말 안 한다** | ❌ 안 건드립니다 (`false` 그대로) |

→ **귀를 열어도 말하기에는 영향이 없습니다.** 읽어주기·음악·타이머 소리는 그대로 나갑니다.

그리고 **봇 자기 목소리는 잡히지 않습니다.** 수신은 `ssrcMap` 으로 **사람별** 스트림을
주는 구조라 봇이 내보내는 소리가 되돌아오지 않습니다 — 읽어주기가 읽는 소리는
나중에 녹음을 만들어도 거기 들어가지 않습니다.

**읽어주기 중에 실행해도 끊기지 않습니다.** 같은 방에 이미 들어가 있으면
`connect()` 가 `joinConfig.channelId` 를 비교해 **그대로 돌려주고**, 진단은
`subscribeTo()` 를 부르지 않습니다. 다른 방에 있으면 옮기지 않고 거절합니다.

### 진단이 지키는 것

- **소리를 어디에도 저장하지 않습니다.** `voice-probe.js` 는 `fs` 를 아예 안 씁니다 (verify 가 검사).
- **실행한 사람이 그 음성방에 있어야** 동작합니다 (5절).
- **다른 방에서 재생 중이면 봇을 옮기지 않고 거절합니다.** 옮기면 듣던 사람 노래가 그냥 끊깁니다.
- 확인이 끝나면 **`finally` 에서 다시 귀를 막습니다** (실패해도).
- **진단 때문에 들어왔으면 끝나고 나갑니다.** `scheduleLeave()` 는 못 씁니다 — 그건
  **사람이 있으면 안 나가는** 규칙(3.3-1)이라 확인을 켠 사람 때문에 봇이 영원히 남고,
  애초에 재생이 끝나는 경로에서만 불려서 재생 없이 들어온 이 경우엔 아무도 안 부릅니다.
  단 **음악·대기열·읽어주기가 하나라도 살아 있으면 나가지 않습니다.**
  원래 들어가 있던 커넥션이면 애초에 건드리지 않습니다.
- `receiver.subscribe()` 는 **받기**, `connection.subscribe()` 는 **보내기**입니다.
  진단은 재생 구독(불변조건 1 의 `subscribeTo()`)을 건드리지 않습니다.

## 2. 실측 결과 — 파이프라인은 이미 있는 것으로 됩니다

**새 의존성이 없습니다.** `@discordjs/voice` 0.19.2 에 수신 API 가, `opusscript` 에 디코더가,
`ffmpeg-static` 에 섞기가 이미 있습니다.

이 PC(i5-1335U)에서 재봤습니다.

| 단계 | 측정값 |
|---|---|
| opus 디코딩 30초 | 79ms — **실시간의 381배속** · 6명분 0.5초 |
| ffmpeg `amix` 로 6명 섞어 m4a | 30초 결과물 **0.89초**, 475KB |

> ⚠️ **소유자 서버는 1 OCPU ARM 입니다. 거기서는 안 재봤습니다.**
> 몇 배 느린지 배수를 추측해서 적지 않습니다 — 그게 위 1절의 두 사고와 같은 실수입니다.
> 서버에서 재보고 이 표에 줄을 추가해야 합니다.

### ★ 계속 녹음 vs 마지막 30초 = 200배 차이

| 방식 | 남는 양 |
|---|---|
| **마지막 30초만** (메모리 링버퍼) | **3.6MB** · 디스크에 안 남음 |
| 4시간 통째로 (6명) | **700MB ~ 1.7GB** (채널 비트레이트에 따라) |

소유자가 말한 **"버튼 누르면 마지막 30초 저장"** 이 훨씬 싼 쪽입니다. 그리고 평소에는
**아무것도 디스크에 안 남습니다** — 30초가 지나면 덮어씁니다.

CPU 도 같습니다. **버퍼에는 opus 를 그대로 담고 디코딩하지 않습니다** (사실상 0).
디코딩·섞기는 **버튼을 눌렀을 때 한 번만** 돕니다.

### 시간 맞추기 — 확인한 제약

수신 스트림은 **RTP 헤더를 떼고 opus 페이로드만** 넘겨줍니다 (`stream.push(packet)`).
즉 **패킷에 시간 정보가 없습니다.** 그리고 디스코드는 **말을 안 하면 패킷을 안 보냅니다.**

→ 도착 시각을 우리가 찍고, 조용한 구간은 무음으로 메워야 합니다. 안 그러면 6명 트랙이
서로 밀려 섞을 때 어긋납니다. **30초짜리 웃긴 순간에는 충분하지만 샘플 단위로 정확하진 않습니다.**

(RTP 헤더에는 타임스탬프가 있지만 `onUdpMessage`·`ssrcMap` 은 공개 API 가 아닙니다.
라이브러리 내부에 손을 넣는 대가가 정확도 이득보다 큽니다.)

## 3. 화면 녹화는 봇으로 안 됩니다

세 가지가 각각 막습니다.

1. **봇은 영상을 아예 못 받습니다.** 디스코드 API 에 영상 수신이 없고 `@discordjs/voice` 도
   지원하지 않습니다. **Go Live 화면은 봇이 닿을 수 없습니다.**
2. **서버에 화면이 없습니다.** 헤드리스 1코어 ARM 입니다.
3. **누군가의 집 PC 에서 돌려야 합니다** — 이건
   [게임방송-기획.md](게임방송-기획.md) **6절에서 OBS 웹소켓을 접은 것과 똑같은 이유**입니다.
   봇이 집 PC 6대에 들어가야 합니다.

### 그런데 이건 이미 있는 기능입니다

NVIDIA **ShadowPlay** / AMD **ReLive** 의 **인스턴트 리플레이**가 바로 "마지막 N초 저장" 입니다.
단축키 하나로 방금 지나간 화면이 저장됩니다.

→ **화면은 각자 PC 의 인스턴트 리플레이, 어디였는지는 망고의 타임라인.**
두 개가 이미 다 있고 나눠져 있을 뿐입니다. **봇으로 다시 만들지 않습니다.**

## 4. 만든 모양 (`src/voice/`)

### ★ 방송 기록과 분리했습니다 (2026-09-08)

처음에는 방송 제어판의 `✂️ 지금!` 에 얹었습니다. 소유자 지적으로 떼어냈습니다.

> "기존 방송 기능과는 분리해줘. /음성기록 이런 별도의 명령어로 만들어줘"

**맞는 지적입니다.** 주 용도가 **방송 없이 그냥 수다 떠는 상황**인데, 방송 제어판에 얹으면
수다를 떨려고 방송을 켜야 합니다. 기능 on/off(`/기능`)도 따로여야 하고요.

| | 방송 기록 | 소리 기록 |
|---|---|---|
| 명령어 | `/방송` | **`/음성기록`** |
| 모듈 | `src/stream/` | **`src/voice/`** |
| 기능 토글 | `stream` | **`voice`** |
| 저장 단위 | 세션 | **날짜 폴더** |
| 목록 파일 | `data/streams.json` | **`data/voice-clips.json`** |

클립 **파일과 용량 예산은 같이 씁니다** (`stream/clips.js`) — 예산을 따로 두면
정리가 소리만 조용히 못 지워, 디스크가 차도 원인을 못 찾습니다.
verify 가 두 모듈이 다시 얽히는 것을 막습니다.

- **명령어는 하나입니다** (3.6-6). 인자 없이 실행하면 **상태 + 버튼 제어판**이 나옵니다.
- **웹 클립 페이지는 이미 `<audio>` 로 재생합니다** (🎧 소리만 배지).
  지난 음성 전용 클립 작업 덕에 받아줄 자리가 이미 있었습니다.

### 흐름 ㄱ — 자동 (권장)

소유자 요청: *"매번 켜는 방식 말고, 사람이 음성채팅방에 들어가면 따라들어와서 자동으로 켤 수는 없을까?"*

```
(한 번만) /관리자 채널설정 종류:소리 기록 음성채널
  ↓
그 방에 2명 이상 모이면  →  봇이 따라 들어와 저절로 켜짐
  ↓
그 방 채팅에 제어판이 뜸  →  웃긴 순간에 ✂️ 지금 30초
  ↓
사람이 빠지면  →  저절로 꺼짐
```

### 흐름 ㄴ — 손으로

```
음성채널에 들어간 다음
  ↓
/음성기록  →  🎙️ 기록 켜기       ← 이때 귀가 열렸는지 확인합니다
  ↓
웃긴 순간 → ✂️ 지금 30초
  ↓
듣기: 클립 웹페이지 (🎧 소리만)
```

### 자동으로 켜는 규칙

| 조건 | 왜 |
|---|---|
| **지정한 방에서만** (`VOICE_AUTO_CHANNEL_ID`) | ⚠️ **비워두면 자동으로 안 켜집니다.** 이미지 채널(비우면 전체)과 **반대**입니다 — 아무 방에서나 남의 대화를 듣게 두지 않으려고, 관리자가 방을 고르게 했습니다 (5절) |
| **2명 이상** (`VOICE_AUTO_MIN_PEOPLE`) | 혼자 있을 때 켜는 것은 의미도 없고 기분도 나쁩니다 |
| 사람이 빠지면 **자동으로 끔** | 켜는 조건만 보면 빈 방에서 계속 켜져 있습니다 |
| **손으로 켠 것은 자동으로 끄지 않음** | 봇이 끄면 "왜 꺼졌지" 가 됩니다 |
| 다른 방에서 재생 중이면 **옮기지 않음** | 옮기면 거기서 듣던 사람의 음악이 그냥 끊깁니다 |
| 제어판을 **그 음성채널 채팅에** 띄움 | 자동으로 켜놓고 버튼이 딴 데 있으면 자동인 의미가 없습니다. 알림은 끕니다 |
| 제어판이 **"자동으로 켜졌습니다"** 를 표시 | 모르고 켜져 있으면 안 됩니다 |

### ★ 같이 잡은 버그 — 읽어주기가 봇을 옮길 때

**읽어주기는 말한 사람의 방으로 봇을 옮깁니다** (`audio.connect()`).
커넥션은 그대로라 수신도 계속되는데, 그러면 **새 방 소리가 30초 전 옛 방 소리와 섞입니다.**
클립을 열어 들어보기 전까지 아무도 모르는 종류의 오류입니다.

→ 인원이 바뀔 때마다 봇이 있는 방과 기록 중인 방을 대조해, 다르면 **버퍼를 버립니다**
(`dropIfMoved`). 읽어주기 음성채널을 고정해두면(`ttsVoiceChannelId`) 애초에 안 옮깁니다.

### 확정한 설계

| 결정 | 이유 |
|---|---|
| `rejoin({ selfDeaf: false })` 로 **켜는 동안만** 귀를 엽니다 | `guild-audio.js` 를 아예 바꾸면 노래 틀 때도 안 쓰는 패킷을 받습니다 |
| **섞은 하나**만 남깁니다 (사람별 트랙 아님) | 웃긴 순간을 다시 듣는 용도입니다. 사람별로 6개면 고르기가 일이 됩니다 |
| 개수는 **하루 단위**로, 영상 클립과 **따로** 셉니다 (`VOICE_MAX_CLIPS`) | 세션이 없으니 세션당으로 셀 수가 없습니다. 한 칸을 나눠 쓰면 수다 30번에 그날 영상 클립을 못 뽑습니다 |
| 용량 예산은 **같이** 씁니다 (`STREAM_CLIP_MAX_GB`) | 따로 두면 정리가 소리만 조용히 못 지웁니다 |
| `✂️` 는 **답을 먼저** 하고 저장은 그 뒤에 | 디코딩·ffmpeg 로 몇 초 걸립니다. 3초를 넘기면 버튼 자체가 실패합니다 |
| 폴더는 **길드 4자리 + 날짜 6자리** | 웹 클립 페이지가 `^[a-z0-9]{4,12}` 패턴만 받고, 서버가 여러 개면 섞이면 안 됩니다 |
| 제어판은 실행한 채널에 **공개로** 남깁니다 | 눌러야 하는 사람이 여럿이고, 웃긴 순간에 눈앞에 있어야 합니다 |
| 재시작하면 제어판을 **꺼진 상태로 고쳐 씁니다** | 링버퍼는 메모리라 재시작하면 꺼집니다. 안 고치면 "기록 중" 이 거짓말로 남습니다 |

### 실측으로 확인한 것 (합성 신호)

무음 메우기가 이 기능에서 유일하게 **조용히 틀릴 수 있는** 곳입니다. 틀려도 소리는 나기 때문에
클립을 열어 들어보기 전까지 아무도 모릅니다. 그래서 순수 함수로 떼어 실제로 돌려봤습니다.

```
A: 0~1000ms 말함 · 1000~3000ms 조용 · 3000~4000ms 말함
B: 500~1500ms 말함

트랙 길이 768000바이트 (= 4000ms × 192) ✅ 정확
A  0~500ms RMS=5643   1500~2900=0 ✅   3100~3900=10682
B  0~400ms RMS=0 ✅    600~1400=6113
섞은 것  0~400=5639   600~1400=7250   1600~2900=0 ✅
클리핑   30000+30000 → 32767 ✅
```

**조용한 구간이 정확히 그 자리에** 있습니다 — 뒤 소리가 밀리지 않습니다.
PCM → m4a 는 표준입력으로 넣어 5.5MB → 323KB, 688ms, 길이 정확히 30.00초였습니다.

## 5. 법 — 한 줄

한국 통신비밀보호법은 **대화 당사자의 녹음은 괜찮지만, 제3자가 남의 대화를 녹음하는 것은
금지**합니다. 봇이 아무도 없는 채널에 상주하며 녹음하면 후자에 가깝습니다.

→ **손으로 켤 때는 켠 사람이 그 채널에 있어야** 합니다. 진단 명령어도 같은 규칙입니다.

**자동으로 켜는 것은 이 규칙을 다르게 지킵니다.** 켠 사람이 그 방에 없을 수 있으니까요.
대신 셋으로 갈음합니다.

1. **관리자가 방을 미리 골라둡니다** (`VOICE_AUTO_CHANNEL_ID`, 비우면 자동 없음).
   봇이 사람을 따라다니며 아무 방이나 듣는 것이 아니라, **그 방은 기록되는 방**이라고
   서버가 미리 합의한 것입니다.
2. **봇이 그 방에 들어와 있는 것이 보이고**, 귀를 열고 있습니다.
3. **그 방 채팅에 "🎙️ 소리 기록 중" 제어판이 뜹니다.** 모르고 켜져 있을 수 없습니다.

그리고 **평소에는 디스크에 아무것도 남지 않습니다** — 30초 링버퍼는 메모리에만 있고
계속 덮어씁니다. 누가 `✂️` 를 눌렀을 때만 파일이 생깁니다. 통째로 녹음해 쌓아두는 것과
성질이 다릅니다.

⚠️ 그래도 **친구들에게 이 방은 기록된다고 알려주는 것**은 소유자 몫입니다.
봇이 할 수 있는 것은 눈에 보이게 하는 것까지입니다.

## 6. 확인하지 않은 것

- **`rejoin({ selfDeaf: false })` 로 귀가 열리는지.** 진단이 실제 상태를 읽어 알려줍니다.
- **패킷이 도착하고 복호화되는지** (DAVE).
- **1코어 ARM 에서 30초 뽑는 데 몇 초 걸리는지.**
- **`selfDeaf: false` 가 음악·읽어주기에 영향을 주는지.**
- **무음 메우기가 실제 대화에서 얼마나 어긋나는지.** 합성 신호로만 재봤습니다.

### 확인 방법

```
(음성채널에 들어간 다음)
/관리자 음성수신확인 초:15
```

두 사람 이상이 **계속 말하면서** 15초를 채워주세요. 한 명만 말하거나 조용하면
"아무 신호 없음" 이 나오는데, 그건 **수신이 막힌 것과 구분이 안 됩니다.**

### 수신이 안 되면 무엇이 보이는가

기능을 켜둔 상태에서 수신이 막혀 있으면 이렇게 나옵니다.

| 언제 | 무엇이 나오나 |
|---|---|
| 🎙️ 켤 때 귀가 안 열리면 | **켜지지 않습니다.** "소리를 받을 수 없어 켜지 않았습니다" |
| 🎙️ 켜졌지만 패킷이 안 오면 | ✂️ 뒤에 **"받은 소리가 없어 남기지 않았습니다"** |
| 복호화가 안 되면 | 위와 같고, 서버 로그에 `[voice-buffer] 수신 오류:` 원문 |

**"받은 소리가 없습니다" 가 버그가 아니라 신호입니다.** 정말 조용했을 때도 같은 말이 나오니,
계속 그러면 `/관리자 음성수신확인` 으로 구분해주세요.

### 권장 구조

```text
망고봇 (현재 Node.js 프로세스)
  └─ 명령어 · 권한 · 제어판 · 클립 파일/웹페이지 관리
                       ↕ localhost IPC/HTTP
녹음 전용 봇 (Rust + Songbird)
  └─ DAVE 음성 수신 · 사람별 Opus · 30초 순환 버퍼
```

현재 망고봇과 녹음 프로세스가 **같은 봇 토큰으로 동시에 한 길드의 음성 연결을 소유하는
구조는 피해야 합니다.** 가장 작은 변경은 테스트용 녹음 봇 계정·토큰을 하나 더 두는 것입니다.
친구들에게 녹음 상태가 보인다는 장점도 있습니다. 별도 봇을 두기 싫다면 음악·읽어주기까지
모든 음성 연결을 Rust 쪽으로 옮겨야 하므로 작업 범위가 크게 늘어납니다.
