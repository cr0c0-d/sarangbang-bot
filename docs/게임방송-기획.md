# 🎬 타임머신 — 유튜브 라이브 하이라이트 자동 기록

여러 명이 각자 유튜브 라이브를 켜고 협동 게임을 할 때, 재미있던 순간을 **버튼 한 번으로 찍어두고**
방송이 끝난 뒤 타임라인 텍스트와 클립 영상으로 뽑아내는 기능입니다.

작성일: 2026-09-03 · 개정: 2026-09-03 (1차 검토 반영 · **Phase 1~3 구현 완료**)
담당 봇: **망고** (`BOT_ROLE=mango`)

### 최신 반영 사항 (2026-09-04)

- 친구용 웹 안내서 `/guide/stream` 추가: 방송 준비부터 클립 저장까지 6단계와 FAQ를 제공합니다.
  실제 캡처는 운영자가 나중에 넣도록 촬영할 화면·파일명·개인정보 가림 안내를 표시합니다.
  후속 작업으로 실제 캡처 13장을 단계별 연결했습니다. 원본 확대 링크와 장면별 설명을 제공하고 사용자의 강조 표시는 유지합니다.
  이미지 제공 검사 포함 1,217개 통과. 로컬 브라우저에서 캡처 로딩을 확인했습니다.
  종료 버튼은 유튜브 종료가 아닌 세션 종료이며, 다시보기 처리 완료 후 추출한다는 점을 구분합니다.
  자체 검사 1,202개 통과. 로컬 브라우저에서 기본/390px 너비 배치와 캡처 자리 표시를 확인했습니다.
  실제 캡처 삽입 후 가독성과 친구 기기의 서버 접근은 운영 환경에서 확인해야 합니다.
- 방송 종료 요약판은 클립 선택 목록을 펼치지 않습니다. 녹화방 자동 공유 메시지의 마지막 장에
  **클립 추출** 버튼을 붙이고, 클릭한 사람에게만 마킹 선택 → 구간 입력 화면을 표시합니다.
  녹화방 미연결용으로 요약판에도 같은 진입 버튼을 남깁니다. 이전 게시물은 요약판 다시 올리기/설명 재제출로 갱신합니다.
  이 흐름의 자체 검사를 포함해 **1,195개 통과**. 실제 Discord 클라이언트에서의 버튼 조작은 운영 확인이 필요합니다.
- 클립 삭제는 인증 필요 시 WEB_TOKEN 입력창을 표시하고 한 번 재시도합니다. 취소하면 파일을 유지합니다.
  삭제 인증 회귀검사를 포함한 자체 검사 **1,184개 통과**. 실제 브라우저 조작은 운영 확인이 필요합니다.
  보기·받기는 공개입니다. 20초 요청 파일이 5초/일반 읽기 0프레임인 사례의 원본은
  종료 후에도 `post_live`(다시보기 처리 중)였고, 해당 구간 재추출은 로컬에서 실패했습니다.
  클립 생성 전 최신 상태를 확인해 처리 중이면 파일 생성 없이 재시도를 안내합니다.
  처리 상태 검사 추가 후 자체 검사 **1,188개 통과**.
  정확한 15초 누락 과정은 미확정이며 기존 파일 복구나 처리 완료 후 정상 추출은 아직 미검증입니다.
- `/방송 게임명`과 `/게임 검색`은 서버에 저장한 한글 별칭도 자동완성합니다.
  포럼 연결 시 제목을 학습하며, 스레드 관리자는 `/게임 검색:<게임> 별칭:<이름>`으로 추가할 수 있습니다.
- 녹화 포스트에는 종료 시 **방송자·시작 날짜·영상 링크·타임라인**을 보냅니다. 미연결 기록은 연결까지 보류합니다.
  설명 수정 시 요약판과 녹화방 게시물을 함께 고치고, 길이에 맞춰 추가 페이지를 생성·삭제합니다.
  공유 마킹은 해당 방송자들도 갱신합니다. 실패 시 설명을 보존하고 재제출을 안내합니다.
- 단순 성공 확인은 사용자·채널별 최신 한 개만 유지합니다. 오류·링크·버튼 화면은 보존하며,
  마지막 확인도 약 14분 뒤 정리합니다. 재시작 전 메시지는 소급 정리하지 않습니다.
- 한글 별칭·녹화방 타임라인 동기화·확인 메시지를 포함한 자체 검사 **1,177개 통과**.
  실제 Discord 권한과 클라이언트 표시 동작은 운영 환경에서 확인해야 합니다.

기능 키: `stream` · 명령어: `/방송` (하나) · customId 접두사: `tm:`

## 0. 확정된 전제

검토 과정에서 소유자가 답한 내용입니다. **이 전제가 바뀌면 3절의 설계도 바뀝니다.**

| 항목 | 확정 |
|---|---|
| 라이브 공개범위 | **전원 "일부공개"** (링크 있는 사람만) → 클립 추출 가능 |
| 라이브 시작 방식 | **"지금 시작"** (예약·대기실 안 씀) → `release_timestamp` 를 믿을 수 있음 |
| 제어판 자리 | **방송 전용 채널**을 만들고 `/채널설정` 으로 지정. 일반 사용자 채팅 금지 |
| 동시 방송 인원 | **최대 6명** → 요약판은 사람당 한 장, 사람당 마킹 25개까지 한 장에 들어감 |
| 한 채널의 세션 수 | **하루에 여러 번** 있음 → `/방송` 상태 화면에 지난 세션 목록이 필요 |
| 클립 화질 | **720p 로 충분** → 낮은 포맷을 고르면 용량이 줄고 재인코딩도 없음 |
| 클립 페이지 권한 | **주소만 알면 누구나.** 라이브 자체가 그렇게 열려 있으므로 클립도 같게 |
| 마킹 입력 | **시간만 기록.** 설명은 게임이 끝난 뒤에 붙임 |

**"비공개"가 아니라 "일부공개"인 것이 결정적입니다.** 진짜 비공개(초대한 사람만) 라이브는
yt-dlp 가 켠 사람 본인 계정의 쿠키 없이는 열지 못하고, 5명이 각자 비공개로 켜면
봇에 5개 계정의 쿠키를 넣어야 해서 만들 수 없습니다. 일부공개는 주소만 있으면 됩니다.

> ⚠️ 다만 **쿠키가 아예 필요 없다는 뜻은 아닙니다.** 유튜브가 서버 IP 를 봇으로 보고 막는
> 문제는 공개범위와 무관하게 그대로 있습니다 (ARCHITECTURE 3.1-4). 음악 봇이 이미
> `YTDLP_COOKIES_FILE` 을 쓰고 있다면 **망고 쪽에도 같은 설정이 필요합니다** — 2.3절 참고.

## 1. 쓰는 흐름 (UX)

### 1-1. 준비 — 방송 채널 지정 (한 번만)

1. 서버에 방송용 텍스트 채널을 하나 만듭니다. (예: `#방송기록`)
2. 그 채널에서 일반 사용자의 **"메시지 보내기"를 끕니다.** 제어판이 채팅에 밀리지 않습니다.
3. `/채널설정` 에서 **"방송 채널"** 을 그 채널로 지정합니다.

> 📌 **"메시지 보내기"를 꺼도 버튼은 눌립니다.** 버튼 클릭은 메시지 전송이 아니라
> 상호작용(interaction)이라 권한이 다릅니다. 단 **"애플리케이션 명령어 사용"** 권한까지
> 같이 끄면 `/방송` 을 못 씁니다. 이건 켜둬야 합니다.

방송 채널을 지정하면 봇이 그 채널에 **[방송 제어판]** 을 하나 올려두고 계속 씁니다.
제어판은 **한 자리에 두고 수정만 합니다.** 채팅이 금지된 채널이라 밀려나지 않습니다.
(요약판을 올려서 밀리는 경우에만 다시 올립니다 — 방송당 한 번이라 도배되지 않습니다)

### 1-2. 방송 등록 — 사람마다 각자

**이번 방송 주소**를 붙여넣습니다.

```
/방송 링크:https://www.youtube.com/live/xxxxxxxxxxx 게임명:<이름>
```

> ⚠️ **전원 일부공개(0절)이므로 방송마다 이렇게 넣어야 합니다.**
> 채널 고정 주소(`@계정/live`)는 **공개 방송만** 찾습니다 — 6절에 근거가 있습니다.
> 공개로 바꾸시면 한 번 등록해두고, 같은 게임은 **[ 🎬 지난 게임으로 등록 ]** 버튼만 누르면 됩니다.

- **참여자 각자가 한 번씩** 등록합니다. 실행한 사람이 그 방송의 주인입니다.
- 같은 사람이 다시 실행하면 자기 링크만 교체됩니다. 늦게 켠 사람도 도중에 끼어들 수 있습니다.
- `게임명` 은 **방송자별**로 저장합니다. 같은 세션이어도 서로 다른 게임을 할 수 있어 각자가 고릅니다.
- 버튼은 검색창을 띄울 수 없으므로 마지막 게임을 재사용합니다. 게임이 바뀌면 `/방송 게임명:…` 으로 다시 고릅니다.
- **인자를 다 비우고 `/방송` 만 치면** 지금 상태(누가 등록했는지·마킹 몇 개인지)와 지난 방송 목록을 봅니다.
  (규칙 3.6-6: 상태 보기용 명령어를 따로 만들지 않습니다)

### 1-3. 마킹 — 버튼 한 번, 입력 없음

제어판의 **[ ✂️ 지금! ]** 버튼을 누릅니다. **그 즉시 시각만 찍히고 끝납니다.**

> 게임 중입니다. 창을 띄우고 설명을 받으면 그 순간은 이미 지나갑니다.
> 설명은 방송이 끝난 뒤 요약판에서 붙입니다 — 그때가 여유도 있고, 영상을 보면서 쓰니 더 정확합니다.

- 누른 사람에게만 `✂️ 찍었습니다 · 00:15:30 · 내 방송 (12번째)` 를 나만 보이게 띄웁니다.
- 실수로 누른 것은 제어판의 **[ ↩️ 내 마지막 취소 ]** 로 지웁니다.
  **내가 찍은 것 중** 마지막을 지웁니다 — 남이 방금 찍은 것을 지우면 안 됩니다.

#### ★ 마킹은 **찍은 사람의 방송에만** 들어갑니다

처음에는 모두의 타임라인에 넣었습니다. 원래 기획이 **"협동 게임"** 전제였기 때문입니다
("다중 접속자의 방송을 동시 추적 중이라면 모두의 타임스탬프를 기록합니다").

**그 전제가 틀렸습니다.** 소유자 지적:

> "동시에 방송은 켰지만 각자 다른 게임을 하고 있을 수도 있거든."

그러면 남의 게임에서 있었던 일이 내 타임라인에 섞이고, **되돌릴 방법도 없습니다.**
그래서 기본을 **"내 방송만"** 으로 바꿨습니다 (`mark.forUserId`).

다 같이 하던 순간은 **찍은 뒤에** 넓힙니다 — 찍은 직후 뜨는 나만 보이는 메시지에
**[ 👥 다 같이 하던 순간 ]** 버튼이 붙습니다. 그 순간은 이미 잡혀 있으니 한 번 더 누를 여유가 있습니다.
이게 마킹을 한 번 클릭으로 유지하면서 협동 게임도 담는 방법입니다.

- 등록을 안 한 사람이 누르면 갈 곳이 없으므로 **그때만** 모두의 것으로 둡니다.
- 넓혀도 **늦게 켠 사람의 음수 마킹은 여전히 빠집니다.** 그 장면이 영상에 없습니다.
- 마킹은 여전히 **세션 하나에 한 줄씩** 저장합니다. 사람별로 복사하지 않습니다 (3.4절).
  "누구 것인가" 는 `forUserId` 한 칸으로 표현하고, 시간은 계산합니다.

### 1-4. 방송 종료 — 아무것도 사라지지 않음

제어판의 **[ ⏹️ 방송 종료 ]** 를 누르면 세션을 닫고 **사람별 요약판**을 출력합니다.

```text
📝 @민수 의 타임라인 · 발헤임 · 마킹 12개
00:15:30  (설명 없음)
01:20:45  어이없이 낙사함
...

[ ✏️ 설명 채우기 ]  [ 🎥 클립 추출 ]
```

- **사람 한 명당 메시지 하나**입니다. 한 장에 다 넣으면 디스코드 상한을 넘습니다 (3.5절).
- 종료는 **되돌릴 수 있어야 합니다.** 마킹은 `data/streams.json` 에 그대로 남고,
  요약판과 클립 버튼은 **재시작을 넘어 계속 동작합니다.** 잘못 눌러도 잃는 것이 없습니다.
- **누구나 누를 수 있는 버튼입니다.** 5명이 아직 게임 중인데 눌릴 수 있으므로,
  닫힌 제어판에 **[ ▶️ 이어서 기록 ]** 을 둡니다. 한 번 누르면 그 세션이 다시 열립니다.
  저장이 비파괴인 것만으로는 부족합니다 — **되돌리는 버튼이 있어야** 실제로 비파괴입니다.
- 요약판 여러 장을 한꺼번에 보내면 채널 전송 한도에 걸립니다. **하나씩 순서대로** 보내고,
  **제어판을 맨 마지막에 다시 올립니다** (그래야 제어판이 맨 아래에 남습니다).
- 유튜브 설명란에 붙일 텍스트는 코드블록으로 감싸 그대로 복사되게 합니다.
- 나중에 설명·클립이 바뀌면 요약판을 **그 자리에서 고쳐 씁니다.** 새로 올리면 클립 5개에
  같은 타임라인이 6장 쌓입니다 (ARCHITECTURE 3.6-9). 그래서 메시지 ID 를 기억해둡니다.
- 요약판이 채팅에 밀려 올라가면 `/방송` 을 인자 없이 쳐서 **다시 올릴 수 있습니다.**
  녹화방 미연결 시에도 클립으로 갈 수 있게 요약판 진입 버튼을 유지합니다.
  이미 공유한 녹화방 게시물도 갱신해 과거 기록에 클립 추출 버튼을 붙입니다.

### 1-5. 클립 추출 — 구간을 직접 조절

녹화방 방송 기록의 **[ 🎥 클립 추출 ]**을 누른 뒤, 본인에게만 열리는
**[ 클립 만들 순간 고르기 ▾ ]**에서 마킹을 고르면 모달이 뜹니다.
목록 쪽 넘기기는 본인의 선택 화면만 바꾸고 녹화방 타임라인 원문은 유지합니다.
버튼에는 세션·방송자 ID가 들어가므로 나중에 봇이 재시작되어도 저장된 기록으로 다시 열립니다.
마킹이 없으면 빈 드롭다운 대신 안내합니다. 추출 뒤 다시 열면 최신 ✅와 클립 보기 링크가 표시됩니다.

| 칸 | 기본값 |
|---|---|
| 시작 시간 | `(마킹 − 15초)` |
| 종료 시간 | `(마킹 + 25초)` |
| 클립 제목 | 마킹 설명 (없으면 빈칸) |

원본을 보고 시간을 고쳐 제출하면 그 구간만 받아서 웹페이지 주소를 나만 보이게 돌려줍니다.

> ⏳ **방송이 끝난 직후에는 추출이 안 됩니다.** 유튜브가 다시보기를 만드는 데 시간이 걸리고,
> `post_live` 상태는 추출 전에 막고 처리가 끝난 뒤 재시도하도록 안내합니다. 처리 시간은 보장하지 않습니다.
> 나중에 녹화방 목록을 훑으며 같은 버튼으로 추출할 수 있습니다.

> 🗑️ **다시보기를 안 남기면 전부 무용지물입니다.** 스트리머가 아카이브를 끄거나 나중에 영상을
> 지우면 타임라인만 남고 클립은 못 뽑습니다. 제어판에 이 한 줄을 적어둡니다.

## 2. 시각 기준 — 여기가 제일 틀리기 쉽습니다

### 2.1 `/방송` 실행 시각을 기준으로 쓰면 안 됩니다

봇이 아는 것은 **명령을 친 시각**입니다. 라이브를 켜고 3분 뒤에 등록하면
**모든 마킹이 3분씩 밀립니다.** 유튜브 설명란에 붙이는 것이 목적인데 전부 어긋난 타임라인이 나옵니다.

### 2.2 `release_timestamp` 를 씁니다 (실측 확인)

yt-dlp 는 **진행 중인 라이브에서도** 실제 방송 시작 시각을 알려줍니다. 직접 확인한 출력입니다:

```
release_ts=1645318623 ts=1645314636 is_live=True status=is_live dur=NA
```

```
yt-dlp --print "%(release_timestamp)s" <라이브 주소>
```

- `release_timestamp` = 방송이 시작된 유닉스 시각. **이걸 t=0 으로 씁니다.**
- **`timestamp` 를 쓰면 안 됩니다.** 게시 시각이라 다릅니다 (위 예시는 66분 차이).
- `NA` 로 나오면 **명령 실행 시각으로 대체**하고, 어긋났다는 것을 사람이 알 수 있게 표시합니다.
- 소유자 확인: 전원 **"지금 시작"** 으로 켭니다. 예약(대기실)을 쓰면 `release_timestamp` 가
  **예약 시각**으로 나올 수 있으니, 나중에 예약을 쓰게 되면 이 절을 다시 봐야 합니다.
- 어긋났을 때는 제어판의 **[ ⏱️ 오프셋 조절 ]** 로 자기 방송만 초 단위로 밀거나 당깁니다.
  (`offsetSec`, 3.4절)

### 2.2a 어긋난 것을 **등록하는 순간** 알 수 있어야 합니다

`release_timestamp` 가 틀리면 **조용히 틀립니다.** 유튜브 설명란에 붙여볼 때까지 아무도 모릅니다.
오프셋 버튼이 있어도 "지금 조절해야 한다"는 사실 자체를 모르면 소용이 없습니다.

→ **등록 확인 메시지와 제어판에 계산된 경과 시간을 같이 보여줍니다.**

```
✅ 등록했습니다 · 방송 시작 21:04 · 지금 8분 진행 중
```

등록하는 사람은 자기 방송이 언제 시작했는지 압니다. 한 시간 전에 켰는데 "8분 진행 중" 이라고
나오면 **읽는 순간 잡힙니다.** 세션이 끝난 뒤에 발견하는 것과는 비교가 안 됩니다.
이게 1차 방어선이고 오프셋 버튼은 그 뒤의 수단입니다.
- 라이브 중에는 `duration` 이 `NA` 입니다. **마킹이 영상 길이 안에 있는지 검사할 수 없습니다.**
  검사는 방송이 끝난 뒤에만 하세요.

마킹의 개인별 타임스탬프는 이렇게 계산합니다:

```
timestampSec = markedAt − stream.startedAt − stream.offsetSec
```

음수가 나오면(그 사람이 늦게 켰다면) 그 사람 요약판에서는 그 마킹을 뺍니다.

### 2.3 망고는 `.env` 만 읽습니다

yt-dlp 설정 일체가 `src/music/ytdlp.js` 에 있고 **`.env.music` 으로 설정됩니다.**
그런데 실행 스크립트를 보면:

```
"start":       "node src/index.js"                        ← 망고: .env 만
"start:music": "node --env-file=.env.music src/index.js"  ← 음악 봇: 둘 다
```

**타임머신을 망고에 두기로 했으므로 `.env` 에도 다음을 넣어야 합니다:**

| 항목 | 왜 |
|---|---|
| `YTDLP_PATH` | 없으면 공식 바이너리를 쓰는데 기동에만 3초씩 걸립니다 (ARCHITECTURE 3.1-2d) |
| `YTDLP_COOKIES_FILE` | 서버 IP 가 막혔을 때. 음악 봇에 넣어뒀다면 여기도 필요합니다 |

> **망고에 두는 것이 맞습니다.** 음악 프로세스는 반응 속도를 오래 다듬어놨으므로
> 거기에 무거운 작업을 얹지 않습니다. 다만 이건 **의식적인 선택**이고, 위 설정 중복이 그 대가입니다.

## 3. 불변조건 (건드리기 전에 읽을 것)

### 3.1 클립은 재인코딩 없이 자릅니다 — 이게 설계의 핵심

`yt-dlp --download-sections "*915-955"` 만 쓰면 키프레임 경계에서 잘라 **그대로 복사**합니다.
yt-dlp 도움말이 직접 말합니다:

```
--force-keyframes-at-cuts     ... This is slow due to needing a re-encode
--no-force-keyframes-at-cuts  (default)
```

- **`--force-keyframes-at-cuts` 를 쓰지 마세요.** 정확해지는 대신 재인코딩이라 1코어에서 몇 분입니다.
  40초 클립에 ±2~3초 오차는 감수합니다.
- 화질도 재인코딩 없이 낮출 수 있습니다. `-f` 로 **낮은 해상도 포맷을 골라 받으면** 됩니다.
  변환이 아니라 선택입니다.
- 긴 방송이어도 **해당 구간만 내려받습니다.** 전체를 받았다가 자르는 것이 아닙니다.

**이 결정이 3.2를 거의 무의미하게 만듭니다.** 복사 모드는 CPU 를 거의 쓰지 않습니다.

### 3.2 직렬화 — 프로세스 안에서만 통한다는 것을 알아둘 것

`ytdlp.js` 의 `serializeExtraction` 은 **모듈 전역 Promise 사슬**입니다.
망고와 노래하는 망고는 **서로 다른 프로세스**라, 망고가 클립을 뽑는 동안 음악 봇이 곡을
추출하면 1코어를 두고 싸웁니다 (ARCHITECTURE 3.1-2b 의 73초 vs 12초 사례).

- 망고 안에서는 `serializeExtraction` 과 같은 방식으로 **한 번에 하나만** 돌립니다.
- **프로세스 간 락은 지금 만들지 마세요.** 복사 모드라 경합이 거의 없습니다.
  실제로 음악이 끊기는 것을 확인한 뒤에 붙입니다 (`data/extract.lock`).

### 3.3 재시작을 견뎌야 합니다

방송은 몇 시간이고, 클립 추출은 방송이 끝난 뒤 며칠 뒤에도 일어납니다.

- 세션·마킹·클립을 전부 `data/streams.json` 에 저장하고, 기동할 때 복구합니다.
- **끝난 세션도 지우지 않습니다.** 요약판의 클립 버튼이 계속 동작해야 합니다.
- 제어판 메시지 ID 는 `src/panel-registry.js` 에 새 종류(`STREAM = 'stream'`)로 기억시킵니다.
  **`sweepOrphanPanels` 의 예외에도 넣으세요** — 안 넣으면 재시작 청소가 제어판을 지웁니다
  (음악 제어판이 `keepMusic` 으로 예외 처리된 것과 같은 방식입니다).
- 요약판은 제어판이 아니므로 훑기 대상이 아닙니다. **다만 `tm:` 버튼이 붙은 메시지를
  제어판으로 오인해 지우지 않도록** 판별을 제어판 전용 customId(`tm:panel:*`)로 좁히세요.

### 3.4 데이터 구조 — 마킹은 세션에 하나씩만, 주인은 한 칸으로

**마킹을 사람별로 중복 저장하지 마세요.** 마킹은 "몇 시 몇 분에 무슨 일이 있었다" 는
**벽시계 사건 하나**입니다. 사람마다 다른 것은 그것을 자기 영상 시간으로 바꾼 결과뿐입니다.
사람별로 복사해두면 늦게 합류한 사람이 생겼을 때 어긋나고, 오프셋을 고칠 때마다 전부 고쳐야 합니다.

**"누구 것인가" 도 복사가 아니라 한 칸입니다** — `forUserId`.
그 사람 id 면 그 사람 방송에만, `null` 이면 모두의 타임라인에 들어갑니다.
`timelineFor()` 가 그 한 칸을 보고 걸러냅니다. (1-3절)

```json
{
  "sessions": [
    {
      "id": "s7k2m9",
      "guildId": "111",
      "channelId": "222",
      "game": "발헤임",
      "openedAt": 1757000000,
      "closedAt": null,
      "streams": [
        {
          "userId": "333",
          "url": "https://youtu.be/AbCdEfGhIjK",
          "videoId": "AbCdEfGhIjK",
          "startedAt": 1757000123,
          "startSource": "release_timestamp",
          "offsetSec": 0
        }
      ],
      "marks": [
        {
          "id": "m1",
          "at": 1757001053,
          "byUserId": "444",
          "forUserId": "444",
          "text": ""
        }
      ],
      "summaryMsgs": { "333": ["999888777"] },
      "clips": [
        {
          "markId": "m1",
          "userId": "333",
          "file": "s7k2m9-q4vx/AbCdEfGhIjK-00-15-30.mp4",
          "startSec": 915,
          "endSec": 955,
          "title": "차에 치임",
          "madeAt": 1757009999
        }
      ]
    }
  ]
}
```

- **사람은 `userId` 로 저장합니다.** 닉네임은 바뀌고, 표시할 때 `<@아이디>` 가 필요합니다.
- `byUserId` = **누가 찍었는지** (취소할 때 씁니다). `forUserId` = **누구 타임라인인지**.
  둘이 다를 수 있습니다 — 내가 찍고 나중에 모두에게 넓히면 `forUserId` 만 `null` 이 됩니다.
- `startSource` 는 `release_timestamp` 또는 `command`. 후자면 요약판에
  "시작 시각을 유튜브에서 못 읽어서 명령 시각을 썼습니다" 를 표시합니다.
- `summaryMsgs` 는 요약판 메시지 ID 입니다. **그 자리에서 고쳐 쓰기 위해** 기억합니다 —
  없으면 클립을 만들 때마다 같은 타임라인이 채널에 쌓입니다 (ARCHITECTURE 3.6-9).
- `clips[].file` 은 `data/clips/<세션id>/` 안의 파일 이름입니다.

### 3.5 디스코드 상한이 요약판 구조를 정합니다

- 버튼은 **메시지당 25개**(5행 × 5)가 상한입니다. 5명 × 마킹 5개면 이미 넘칩니다.
- 드롭다운도 **선택지 25개**가 상한입니다. 바꿔도 마찬가지입니다.
- → **요약판은 사람당 메시지 하나**, 클립 선택은 **드롭다운**. 마킹이 25개를 넘으면 페이지를 나눕니다.
- 이건 나중에 붙일 수 없는 구조 문제입니다. **처음부터 이렇게 짜세요.**

### 3.6 빌더에 `null`·`""` 금지

모달·임베드를 조립할 때 빈 값이 들어가면 상호작용이 **조용히 실패**합니다 (명령어 무반응).
값이 없으면 그 메서드를 아예 호출하지 마세요. 새 화면은 `verify.mjs` 의 화면 조립 검사에 추가합니다. (규칙 7-1)

설명 채우기 모달에서 특히 두 가지를 조심하세요.

- **칸마다 `setRequired(false)` 를 명시**하세요. 안 하면 5칸 중 2칸만 채운 사람이
  빠져나갈 수 없는 검증 오류를 만납니다.
- **설명이 없는 마킹에는 `setValue` 를 아예 호출하지 마세요.** `setValue('')` 가 바로
  위의 조용한 실패입니다 — 모달이 안 뜨고 버튼이 고장난 것처럼 보입니다.

### 3.7 파일 경로

`data/clips/<세션폴더>/<파일명>.mp4` 에 저장합니다.

- 경로는 항상 `node:path` 로 조립합니다. 문자열 이어붙이기 금지.
- 폴더·파일 이름은 `src/images/store.js` 의 `safeFolderName()` / `safeFileName()` 과 같은 방식으로
  걸러야 합니다. 세션 폴더 이름에는 **사람이 지은 문자열(게임명)을 넣지 마세요.**
- 세션 폴더 이름은 **세션 id** 를 그대로 씁니다. id 자체가 무작위 6글자입니다.

### 3.8 웹페이지 — 갤러리와 완전히 같은 방식

기존 갤러리의 인증 경계(ARCHITECTURE 3.6-3)를 그대로 따릅니다.
**보기는 주소만 알면 누구나, 삭제만 `WEB_TOKEN`.**

소유자 확인: 라이브 자체가 일부공개(주소만 알면 누구나)라서 **클립을 더 잠글 이유가 없습니다.**
같은 사람들이 같은 주소를 돌려 보는 구조입니다.

- 새 라우트: `/c/:folder` (목록) · `/clip/:folder/:file` (재생) · `/cdl/:folder/:file` (저장).
- **`res.sendFile` 을 쓰면 Range 요청이 자동으로 처리됩니다.** 브라우저에서 재생 중 탐색이 됩니다.
- `src/images/store.js` 를 클립용으로 고치지 마세요. **별 파일**(`src/stream/clips.js`)에
  같은 안전장치를 두는 편이 낫습니다. 사진 저장 경로는 이 저장소에서 가장 위험한 곳입니다.

### 3.9 용량 — Phase 2 에서는 개수 상한만

`src/images/cleanup.js` 는 `images/store.js` 에 강하게 묶여 있습니다. "논리를 적용"하는 것이
곧 리팩터링입니다. 그리고 그 파일은 **사용자 데이터를 영구 삭제**합니다 (ARCHITECTURE 3.6-5).

- **Phase 2:** 세션당 클립 20개, 전체 200개 상한. 넘으면 오래된 것부터 지우고 알립니다. 이게 훨씬 쌉니다.
- **Phase 3:** 별도 예산(`CLIP_MAX_GB`)으로 자동 정리. `cleanup.js` 를 일반화하는 작업과 함께.

### 3.10 이 저장소의 일반 규칙

- 기능 키 `stream` 을 `settings.js` 의 `FEATURES` 에 추가하면 `/기능` 으로 켜고 끌 수 있습니다.
  명령어는 `commands.js` 에서 `tag('stream', ...)` 로 감쌉니다. **명령어 안에서 직접 검사 금지** (3.7-1)
- 설정 항목 `streamChannelId` 를 `settings.js` 의 `KEYS` 에 넣으면 `/채널설정` 선택지가 따라옵니다.
  읽을 때는 반드시 `get` / `getWithSource` 로 읽습니다. `config.*` 직접 읽기 금지 (3.8)
- customId 접두사는 `tm:` 입니다. 이미 쓰이는 것: `c: f: g: m: mv: pl: st: t: tts: v:`
- **`flushStreams()` 를 `shutdown()` 에 넣으세요** (`flushPlans` 옆). 안 넣으면 재시작 직전
  몇 초 사이의 마킹이 사라집니다. **그게 안 사라지는 것이 이 기능의 존재 이유입니다.**
- **마킹 버튼은 답을 먼저 하고 제어판을 나중에 고칩니다.** 제어판 수정이 앞에 오면
  전송 한도에 걸릴 때 가장 많이 눌리는 버튼에서 "Unknown interaction" 이 납니다.
- **`--print` 호출에는 제한시간을 따로 주세요** (약 10초/20초). `timeoutLadder()` 는
  음악 추출 실적으로 자기를 조정하는데, 망고 프로세스에는 그 실적이 없어서
  기본 20초/40초를 씁니다. 메타데이터 한 번 읽는 데 1분을 기다리면 고장으로 보입니다.
- **링크 형태를 세 가지 다 받으세요.** 라이브는 유튜브가 **`youtube.com/live/<id>`** 를 줍니다.
  `watch?v=` 만 보면 실제로 붙여넣는 형태에서 등록이 실패합니다.
  (`youtu.be/`, `music.youtube.com` 도 포함. `music/commands.js` 의 `YOUTUBE_RE` 참고)
- 사용자에게 보여줄 오류는 `src/user-error.js` 의 `userError()` 로 만듭니다.
- **yt-dlp 가 실패한 원인을 추측해서 적지 마세요.** `ytdlp.js` 의 `friendlyError` / `rawError` 를
  그대로 씁니다. 모르면 원문을 보여주세요 (3.1-4).
- `/도움말` 에 항목을 추가하고, `verify.mjs` 에 검사를 추가하고, 명령어를 바꿨으면 `npm run deploy`.

## 6. OBS 자동 시작을 만들지 않은 이유

원래 기획의 "OBS Webhook 연동" 은 **미확인**으로 남겨뒀던 항목입니다. 확인했고, **접었습니다.**

**obs-websocket 은 OBS 가 서버입니다.** 외부 도구가 클라이언트로 붙는 구조입니다
([obs-websocket](https://github.com/obsproject/obs-websocket)). 밖으로 알림을 보내지 않습니다.
그래서 봇이 **각자의 집 PC 로 접속해 들어가야** 하는데, 6명분 포트 개방이 필요합니다.

OBS 스크립트(Lua)로 우리 쪽을 호출하게 만들 수는 있습니다. 그래도 소용이 없습니다 —
**OBS 는 스트림 키만 알고 유튜브 방송 주소를 모릅니다.** 사람이 링크를 붙이는 일이 그대로 남습니다.
게다가 토큰 없는 공개 엔드포인트를 열면 자동 스캐너에 금방 발견됩니다.

### 대신: 고정 주소를 기억합니다

목적은 "매번 링크 붙이지 않기" 였습니다. 그건 훨씬 싸게 됩니다.
유튜브의 채널 고정 주소는 방송마다 바뀌지 않고, **yt-dlp 가 그걸 지금 하는 방송으로 풀어줍니다.**
직접 확인한 출력입니다:

```
youtube.com/@ABCNews/live → id=iipR5yUp36o  release_ts=1746107641  status=is_live
```

- 사람마다 **한 번만** `/방송 링크:https://www.youtube.com/@내계정/live` 로 등록합니다.
- 같은 게임이면 그다음부터는 제어판의 **[ 🎬 지난 게임으로 등록 ]** 버튼 하나입니다. 늦게 켠 사람도 도중에 끼어듭니다.

### ⚠️ 그런데 이건 **공개 방송에서만** 됩니다 (2026-09-03 확인)

**처음에 이걸 놓치고 "추천" 으로 적었습니다.** 위 실측은 **공개** 뉴스 채널이었고,
그걸 이 서버의 **일부공개** 설정에 일반화한 것이 잘못이었습니다. 소유자가 바로 막혔습니다:

> "일부공개로 하고 방송시작했는데 /방송 으로 등록하면 지금 방송중이 아니라고 떠"

라이브 중이 아닌 채널의 `/live` 에 대해 yt-dlp 는 이렇게 답합니다:

```
ERROR: [youtube:tab] @Google: The channel is not currently live
```

**일부공개는 채널 목록에 안 뜨므로 같은 답이 옵니다.** "일부공개" 의 정의가 그것입니다.
게다가 `friendlyError` 가 이 문장을 **영어 그대로** 넘겨서, 원인을 짐작할 수도 없었습니다.

→ 지금은 `registerStream` 이 이 문장을 **가로채서** 사정을 설명하고
**이번 방송 주소를 넣으라고** 안내합니다. 0절이 "전원 일부공개" 이므로 **그게 기본 경로**이고,
고정 주소는 접어둔 선택지로 남깁니다.

⚠️ **교훈: 실측한 조건 밖으로 결론을 늘리지 말 것.**
공개 스트림으로 확인한 것은 공개 스트림에 대한 사실입니다.
- ⚠️ **`watch?v=` 형태는 저장하지 않습니다.** 그건 그 방송 하나만 가리켜서, 저장하면
  **매번 지난 방송을 등록하게 됩니다.** 2.2a 가 잡으려는 바로 그 조용한 오류입니다.
- ⚠️ 고정 주소로 조회했는데 방송이 없으면 **주소 문제가 아닙니다.** 아직 안 켠 것입니다.
  "주소를 확인하세요" 라고 하면 멀쩡한 주소를 들여다보게 만듭니다.

## 7. 구글 드라이브 업로드 — **검증하지 못했습니다**

`src/stream/drive.js` 에 있습니다. 다른 기능들과 **믿음의 근거가 다릅니다.**

이 세션의 나머지는 전부 실제로 돌려보고 만들었습니다 — `--download-sections` 를 돌려
`copy` 모드를 확인했고, `@계정/live` 를 풀어 id 를 받아봤습니다. **드라이브는 자격증명이
필요해서 그러지 못했습니다.** `verify` 는 "우리 코드가 의도한 요청을 만드는가" 만 봅니다.
**구글이 그 요청을 받아주는지는 확인되지 않았습니다.**

그래서 다음 두 가지를 지켰습니다.

- **로컬 파일을 지우지 않습니다.** 사본만 올립니다. 올렸다고 해놓고 반쪽만 갔을 때
  원본까지 지우면 클립이 사라지고 웹페이지가 404 가 됩니다. 되돌릴 방법이 없습니다.
  로컬 파일은 기존 예산·개수 상한이 관리합니다. → **드라이브는 더하기만 하는 기능입니다.**
  안 되면 답에 오류 한 줄이 붙고 나머지는 그대로입니다.
- **구글이 한 말을 원문으로 보여줍니다.** 원인을 지어내지 않습니다 (3.1-4).
  처음 쓸 때 오류가 나면 그 원문이 답입니다.

설정을 안 하면 **조용히 꺼집니다.** 클립은 웹페이지에서 그대로 보고 받을 수 있습니다.
`googleapis` 패키지는 쓰지 않았습니다 — REST 세 번이면 되는 일에 의존성을 늘리지 않습니다
(TMDB·제미나이와 같은 방식).
