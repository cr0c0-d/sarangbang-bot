대상: **망고** (`BOT_ROLE=mango`)
작성일: 2026-09-01
상태: **설계 단계. 코드 없음.** 아래 「결정이 필요한 것」을 정하고 나서 구현합니다.

## 0. 한 문단 요약

친구들끼리 "언제 만날까 / 뭐 챙길까" 를 정하는 기능. 요청은 "일정 관리" 와 "여행 계획"
두 개였지만, 실제로 필요한 것을 파보면 **부품 두 개**로 환원된다 — **날짜 조율**(여러 날짜 중
각자 가능한 날을 **여러 개** 고르기)과 **체크리스트**(누르면 켜지는 목록). 알림은 이미 있는
타이머 부품을 그대로 쓴다. 캘린더 앱을 만들지 않는다.

---

## 1. 요청을 그대로 만들면 실패한다

"일정 관리" 를 글자대로 만들면 캘린더 앱이 된다. 월별 보기, 반복 규칙, 초대, 참석 여부,
알림 설정… 디스코드 안에서 그걸 다 하는 건 만들 수도, 쓸 수도 없다.

**친구들 모임에서 실제로 막히는 지점은 하나다.**

> "다음 주에 만나자" → "나 화요일 안 돼" → "그럼 목요일?" → "나 목요일 저녁만" → …
> (카톡 20줄 뒤에도 안 정해짐)

이게 **날짜 조율**이다. 여행 계획도 마찬가지로 여기서 막히고, 정해진 뒤에는
"뭐 챙기지 / 어디 갈까" 로 넘어간다. 그건 **체크리스트**다.

그래서 이 기획은 캘린더가 아니라 **저 두 부품**을 만드는 것으로 잡는다.

---

## 2. 부품 1 — 날짜 조율 (복수 선택 투표)

### 2.1 지금 투표로는 안 되는 이유

기존 `/투표`(3.6-7)는 **한 사람이 하나만** 고른다. 날짜 조율은 반대다 —
**"내가 가능한 날 전부"** 를 골라야 하고, 그중 겹치는 날을 찾는 게 목적이다.

즉 필요한 것은 **복수 선택 투표**다. 투표 부품을 확장하면 된다.

```
📅 다음 모임 언제?

  10/3 (금)  ██████░░░░  4명  ← 최다
  10/4 (토)  █████░░░░░  3명
  10/5 (일)  ██░░░░░░░░  1명
  안 되는 날만 있음         1명

  [10/3] [10/4] [10/5] [❌ 다 안 됨]     ← 여러 개 눌러도 됨
  [🔒 마감]
```

- 버튼을 누르면 **토글**된다. 여러 날을 켤 수 있다.
- 누가 어느 날을 골랐는지는 **보여줘야 한다.** 단순 투표와 다른 점이다 —
  "3명 가능" 만 알면 누구를 설득해야 할지 모른다.
  (기존 투표는 익명이었다. 이건 **의도적으로 다르게** 간다)
- 마감하면 **최다 득표일이 확정**되고, 그 일정에 알림을 걸 수 있다.

### 2.2 날짜 후보를 어떻게 입력받나

여기가 사용성의 전부다. `10/3, 10/4, 10/5` 를 타이핑하게 하면 안 쓴다.

**제안: 모달 한 칸 + 자유 입력, 우리가 해석한다.**

```
언제 만날까?        ← 질문 (기본값: "다음 모임 언제?")
날짜 후보          ← "10/3~10/5" 또는 "금 토 일" 또는 "10월 3일, 5일, 7일"
```

`이번 주말` `다음 주 평일` `10/3~10/7` 같은 말을 날짜 목록으로 바꾼다.
타이머의 `15분` `1시간 30분` 해석기와 같은 발상이다(3.4-2) — **사람이 쓰는 대로 받고,
우리가 이해한 결과를 보여준다.** 못 알아들으면 무엇을 어떻게 쓰면 되는지 예시를 준다.

> 대안: 드롭다운으로 날짜를 하나씩 고르게 하기. 정확하지만 25개 제한이 있고
> 여러 번 눌러야 한다. **1차는 자유 입력으로 가고**, 해석 실패가 잦으면 그때 드롭다운을 덧붙인다.

### 2.3 확정 후

마감하면 확정된 날짜로 **일정**이 하나 생긴다. 그 뒤는 부품 3(알림).

## 3. 부품 2 — 체크리스트

여행 준비물, 갈 곳 목록, 할 일. **전부 같은 모양**이다.

```
🧳 오사카 여행 준비물

  ✅ 여권            (지예)
  ✅ 보조배터리       (민수)
  ⬜ 우산
  ⬜ 멀티어댑터

  [여권] [보조배터리] [우산] [멀티어댑터]    ← 누르면 ✅/⬜ 토글 + 담당자 표시
  [➕ 항목 추가]
```

- 누르면 켜지고, **누가 챙기는지** 자동으로 붙는다. 담당자를 따로 지정하지 않아도 된다.
- `➕ 항목 추가` 는 모달로 여러 줄을 한 번에 받는다 (투표 선택지와 같은 방식).
- 항목이 25개를 넘으면 버튼이 넘친다 → **한 판에 25개까지**, 넘으면 목록을 나눈다.

이 하나로 준비물·갈 곳·할 일이 다 된다. **종류별로 따로 만들지 않는다.**

## 4. 부품 3 — 알림 (이미 있는 것을 쓴다)

`timer/index.js` 가 이미 갖고 있는 것:

- `data/timers.json` 에 저장 → **재시작을 견딘다**
- 켜질 때 되살리고, 지난 것은 즉시 처리
- 음성채널에 있으면 소리로, 없으면 채팅으로 알림

일정 알림은 **같은 구조를 그대로 쓴다.** 새로 만들지 않는다.
다른 점은 "며칠 뒤" 라는 길이뿐이다 — 타이머 상한이 지금 며칠인지 확인해서
필요하면 늘린다(setTimeout 한계 약 24.8일).

**알림 시점 제안**: 하루 전 저녁 + 당일 아침. 그 이상 세분화하면 설정만 늘어난다.

## 5. 그래서 무엇이 만들어지나

### 5.1 명령어

| 명령어 | 여는 것 |
|---|---|
| `/일정` | 판 → `[📅 날짜 조율]` `[📋 다가오는 일정]` `[✈️ 여행 만들기]` |
| `/여행` | 위 판의 **여행 지점을 바로 연다** |

**`/여행` 은 별도 기능이 아니라 같은 판의 다른 입구다.** 코드는 하나다.
친구가 "여행 계획" 을 떠올렸을 때 `/여행` 을 칠 것이므로 발견 가능성 때문에 둔다.
(이게 과하다고 판단되면 `/일정` 하나로 줄인다 — 「결정이 필요한 것」 참고)

### 5.2 여행 = 일정 + 체크리스트 묶음

여행을 따로 만들지 않는다. **여행은 "날짜가 정해진 일정 + 딸린 체크리스트들"** 이다.

```
✈️ 오사카 여행          10/3(금) ~ 10/6(월)

  [🧳 준비물]  [📍 갈 곳]  [💰 비용]      ← 각각 체크리스트
  [🔔 알림 켜기]  [✏️ 날짜 바꾸기]
```

`💰 비용` 은 1차 범위 밖이다 (아래 참고).

### 5.3 새 파일

```
src/plan/
  parse-dates.js   "이번 주말", "10/3~10/5" → 날짜 목록  (verify 로 촘촘히 검사)
  store.js         data/plans.json — 일정·체크리스트 저장 + 알림 예약 복구
  index.js         /일정 · /여행 명령어와 버튼 판
```

- `FEATURES` 에 `plan` 추가 → `/기능` on/off 자동 편입 (3.7-1)
- 버튼 앞머리 **`pl:`**
- 고른 상태는 **customId 에 싣는다** (3.6-8 과 같은 이유 — 메모리 Map 금지)

## 6. 하지 않는 것 (Non-goals)

| 안 하는 것 | 왜 |
|---|---|
| 월별 캘린더 화면 | 디스코드 임베드로 표 그리기는 읽기 어렵다. 목록이 낫다 |
| 반복 일정 (매주 목요일) | 2차. 규칙 입력 UI 가 커진다 |
| 구글 캘린더 연동 | OAuth + 토큰 보관 + 갱신. 개인 서버 셋에 과하다 |
| 참석 여부(예/아니오/미정) | 날짜 조율이 그 역할을 이미 한다 |
| **비용 정산** | 돈 계산은 틀리면 안 되는 기능이다. 누가 얼마 냈고 누가 얼마 받을지, 통화·반올림·정산 순서까지 정해야 한다. **별도 기획으로 떼어낸다** |
| 외부 알림 (문자·메일) | 디스코드 안에서 끝낸다 |

## 7. 단계

1. **`parse-dates.js`** — 날짜 해석기부터. 여기가 사용성의 전부이고, 토큰 없이 검증 가능하다.
   verify 에 표현 수십 가지를 박아둔다.
2. **날짜 조율** — 복수 선택 투표. 기존 투표를 확장할지 별도로 둘지는 아래 결정 사항.
3. **일정 + 알림** — 타이머 구조 재사용.
4. **체크리스트** — 준비물·갈 곳.
5. **여행 묶음** — 3+4 를 하나로 묶는 화면.
6. `/도움말` · README · verify.

각 단계는 **단독으로 쓸 수 있는 상태**로 끝낸다 (CLAUDE.md 원칙).
1~2 만 있어도 "언제 만날까" 가 해결되므로 그 자체로 가치가 있다.

## 8. 결정이 필요한 것

1. **명령어를 `/일정` 하나로 할지, `/여행` 도 둘지.**
   하나면 명령어가 16개, 둘이면 17개다. 발견 가능성 대 목록 길이의 맞바꿈.

2. **복수 선택 투표를 기존 `/투표`에 넣을지, 날짜 조율 전용으로 둘지.**
   - 기존에 넣기: `/투표` 창에 "여러 개 고르기 허용" 칸 추가. **그런데 모달 칸이 이미 5개(한도)다.**
     칸을 빼거나 다른 방법을 찾아야 한다.
   - 전용으로 두기: 날짜 조율은 이름이 보이고(익명 아님) 날짜를 자동 생성하므로
     어차피 다르게 동작한다. **이쪽을 권한다.**

3. **날짜 후보 입력을 자유 입력으로 시작할지.**
   권한다. 다만 "이번 주말" 같은 말을 어디까지 알아들어야 하는지 목록이 필요하다 —
   실제로 쓸 표현을 몇 개 알려주면 그것부터 지원한다.

4. **알림 시점** — "하루 전 저녁 + 당일 아침" 으로 고정할지, 고를 수 있게 할지.
   고정을 권한다. 설정을 늘리면 아무도 안 만진다.

5. **비용 정산을 이번에 넣을지.** 위에서 뺐지만, 여행에서 실제로 제일 귀찮은 일이기도 하다.
   원한다면 **별도 기획**으로 먼저 정리하는 편이 안전하다.
